# Release v6.12.0 contract

This contract binds the release candidate, the release artifacts, the price sidecar, the upgrade rehearsal, the fleet rollout, the cut-over of the data services and the application, rollback, post-rollout verification, the operator inputs and the retirement of the v6.11 name for the Paxeer X Network node binary paxd at v6.12.0. Code citations are at revision 211acbc6c of github.com/Sidiora-Labs/Paxeer-X-Network unless prefixed `Launch-x:` (commit c5eb7c7 of github.com/Sidiora-Labs/Launch-x). Paths under `tools/release/` that do not exist at that revision are planned paths created by the tasks of this feature.

## Build and plan

1. Base. The release candidate is built from the main branch at the revision on which every implementation feature is done: the baseline wiring tasks 1.0.1 and 1.3.100 and the domain completion tasks of features 2 to 7, the rule of the feature 8 completion task. Every later step names that revision as `RELEASE_COMMIT`.
2. Plan name. The upgrade plan is named `v6.12.0`. It is declared as `V6120Upgrade = "v6.12.0"` in `node/upgrades_v6120.go` by baseline task 1.0.3, listed in `knownUpgradePlans` (node/upgrades.go:530-534) and registered with `SetUpgradeHandler` beside the existing plans (node/upgrades.go:199-209). The Release Check identity step (.github/workflows/paxeer-release-check.yml:45-49) greps today for any `= "<upgrade>"` declaration, which GovernanceActivationUpgrade (modules/layerxcustody/types/governance_activation.go:5) already satisfies; the required change makes it grep for the `V6120Upgrade` declaration. The plan v6.11 is removed and its SID work runs as hooks of the v6.12.0 handler (section Name retirement).
3. Release identity. `tools/release/version.json` (tools/release/version.json:1-4) holds `{"version": "v6.12.0", "upgrade": "v6.12.0"}`. The version must match the semantic version pattern of .github/workflows/paxeer-release-check.yml:39-44 and be newer than every `paxeer-network/v*` tag (.github/workflows/paxeer-release-check.yml:57-65).
4. Tag. The release tag is `paxeer-network/v6.12.0` (tools/release/build-paxd.sh:19-20). The tag namespace is the one chain.mk resolves for its version string (chain.mk:9).
5. Toolchain. The build refuses to run unless `go env GOVERSION` equals the `go` line of go.mod (tools/release/build-paxd.sh:11-17, go.mod:3), with `GOTOOLCHAIN=local`. The Rust toolchain is the channel of rust-toolchain.toml:2, checked by the release script. The C compiler is pinned by `CC_VERSION` of `tools/release/toolchain.env`; the release script refuses a compiler whose `cc -dumpfullversion` differs, and both release workflows install that compiler.
6. Kernel libraries. Before the Go build, the release script runs `make paxd-native-libs`, the Makefile target the baseline wiring adds, which builds the kernel static library `build/liblayerx.a` (Makefile:46, Makefile:211) and the release sandbox static library `programs/target/release/liblayerx_programs_sandbox.a` through `programs-release-build` (Makefile:3406, Makefile:3422-3425); baseline task 1.0.1 points the target at the release library, not the debug one of Makefile:3405. These are the link directories and libraries that modules/lxphost/host.go:6-7 names. The release script reads tools/release/version.json and the version check of the baseline wiring reads it too; only the release tasks edit it.
7. Version stamp. The binary carries `Version=v6.12.0`, `Commit=RELEASE_COMMIT` and `BuildTags=netgo,ledger` through the linker flags of tools/release/build-paxd.sh:35-41. The application hands the version to the base application (node/app.go:593), which reports it as `version` in the ABCI info response (sdk/baseapp/abci.go:98) served at the CometBFT `abci_info` route (consensus/internal/rpc/core/routes.go:71).
8. Determinism inputs. `SOURCE_DATE_EPOCH` is the commit time of `RELEASE_COMMIT` (tools/release/build-paxd.sh:22); the Go build runs with `-trimpath -buildvcs=false` and an empty build id (tools/release/build-paxd.sh:36, tools/release/build-paxd.sh:44); C and Rust paths are remapped to repository-relative prefixes, as the layerxd build already does with `-ffile-prefix-map` (tools/release/build-paxd.sh:64-65).

5. Reproducibility. ## Upgrade rehearsal

1. Purpose. The rehearsal applies plan v6.12.0 to the real chain state at a halt height on a local network of four validators of equal power, the consensus shape of the fleet, before any fleet host is touched.
2. Inputs. A copy of the data directory and genesis of a stopped, synced full node; the running release binary as the old binary; the release candidate as the new binary; the Chainflow feed configuration of contracts/pricefeed.md for the local price sidecars. All are named in an untracked copy of `tools/release/env/rehearsal.env.example`, the pattern of the fork rehearsal (platform/hosted/paxeer/fork-rehearsal.sh:25-31).
3. Export. The old binary exports the copied state with `paxd export --height <E>` (sdk/server/export.go:191), as the fork rehearsal exports (platform/hosted/paxeer/fork-rehearsal.sh:334-358).
4. Validator set. The exported genesis is rewritten so each of the four bonded validators keeps its operator, tokens and delegations and takes a disposable local consensus key; the CometBFT validator list and the slashing signing infos follow the new keys; the result passes `paxd validate-genesis` (platform/hosted/paxeer/fork-rehearsal.sh:444-445).
5. Halt. The four local nodes run the old binary with `--halt-height HR`; each commits HR and halts itself (sdk/baseapp/abci.go:310, sdk/baseapp/abci.go:322) with the log line `halting node per configuration` (sdk/baseapp/abci.go:360), a key=value line carrying `height=HR`. The application hash at HR is recorded and every home is archived with `tools/release/snapshot.sh`.
6. Upgrade. Each home receives the node upgrade file `{"name": "v6.12.0", "height": HR+1}`; the four nodes restart on the new binary and apply the plan in block HR+1 (node/upgrades.go:574-604), logging `applying upgrade` once (node/upgrades.go:602).
7. Assertions. The rehearsal passes only when all of these hold on all four nodes:
   - `paxd q upgrade applied v6.12.0` reports height HR+1 (platform/hosted/paxeer/fork-rehearsal.sh:536-540 is the existing query shape);
   - the ABCI info version is `v6.12.0`;
   - block HR+1 and every later block carry the same block hash on all four nodes, and the chain passes HR+10;
   - every served address of contracts/address-table.md answers its view call without revert at HR+1, each of 0x1020-0x1025 answers `0x` at HR (precompile presence switches at the activation height), and 0x1026 and 0x1027 answer `0x` at HR and at HR+1;
   - the launchpad pool count `getPoolCount()` (Launch-x:contracts/contracts/interfaces/IPoolRegistry.sol:63) served by 0x1017 equals the sum of the pool counts of the two deployment-generation registries read at HR (Launch-x:contracts/contracts/data/PoolRegistry.sol:111-113), and every migrated pool returns the reserves `getReserves()` (Launch-x:contracts/contracts/interfaces/ISidioraPool.sol:65-69) its contract returned at HR;
   - the perpetuals market count is eighteen, with the markets of contracts/perps-markets.md;
   - one feed key per validator is registered with registerFeedKey after the operator EVM address is associated, getFeedKey returns it, and after the four local price sidecars run `getPrice(m).fresh` is true for every market of contracts/pricefeed.md;
   - the uhpx and SID pointers answer through getNativePointer of 0x100A with decimals 6, and the USDL ERC20 answers decimals() 6;
   - the programme checks of `tools/release/rehearsal/programme.py` pass: launchpad interface, USDL ERC20 custody, pool parity, fee right and pool token, perpetuals order types, margin, economics, markets and log rebuild, spot interface, settlement and logs, sidecar submissions, price freshness and submission bounds, plan and version;
   - no node log carries `panic`;
   - the rollback leg passes: after HR+10 the four nodes halt, `tools/release/rollback.sh --execute` restores each home's snapshot and the previous binary, the nodes restart, the application hash at HR equals the recorded one and the chain passes HR+5.
8. Result. The rehearsal writes `rehearsal-result.env` with `upgrade`, `halt_height`, `export_height`, `final_height`, `old_bin_sha256`, `new_bin_sha256`, `pools`, `markets`, `oracle_fresh`, `feed_keys`, `precompiles_served`, `rollback_rehearsed`, the key set of platform/hosted/paxeer/fork-rehearsal.sh:568-576 extended by the last six; its receipt `tools/release/rollout/v6.12.0/rehearsal.json` uses the receipt key set of section Post-rollout verification. `new_bin_sha256` must equal the `SHA256SUMS` line of the release.

## Rollout

1. Roles. Validator hosts run validator homes; a validator host may also run a full node and every unit on one host shares one installed paxd binary. Full-node hosts run one full node each; one full node is the archive node. The edge proxies the public endpoints. The build host builds the release. The operations host runs fleet automation (watchdog and resync timers) and the verification script.
2. Mechanism. The fleet uses the operator-file path: every validator halts at H with `--halt-height H`, every home receives the node upgrade file for H1 = H + 1, and every node restarts on v6.12.0. The governance-proposal path of docs/runbooks/paxeer-x-fork.md:119-214 is not used for this release.
3. Order. Halt-height approval; preflight; stage binaries; stop and disable the old feeder and pause automation; freeze validators at H; snapshot of every validator and full-node home at H; full-node swap; validator swap and start; feed-key registration and price sidecar install; cut-over of the data services and the application; lagging nodes and the archive node; resume automation; rollback readiness; post-rollout verification; the spot-open application build. The steps, commands and checks are in docs/rollout-runbook.md; every step writes one receipt under `tools/release/rollout/v6.12.0/`.
4. Invariants.
   - No unit runs v6.12.0 before every validator has committed H on the old binary; a host whose binary is shared is swapped only after every validator home on it has halted.
   - Every height is written as a literal number into every remote command.
   - Process checks match the exact process name (`pgrep -a -x paxd`); a pattern match against a full command line is not used.
   - Every swap is atomic (`cp -p` to a temporary name in the same directory, then `mv -f`) and checked against the release sha256 and with `ldd` (no `not found` line) before the unit starts.
   - Every validator and full-node home is archived after it halted or stopped at H and before its binary is swapped.
   - The earlier feeder `layerx-oracle-feeder` (platform/hosted/feeder/src/lib.rs:62) is stopped and disabled on every host before H and never restarted.
   - Fleet automation that restarts, reclones or replaces binaries is stopped for the whole window and resumed only after verification passes.
   - Data moves and age-based deletion are never paired in one run; set-aside data is removed only by an explicit operator decision.
   - The archive node is never recloned.
5. Operator inputs. See section Operator inputs.

## Rollback

1. Trigger. Rollback runs when the validators, oracle, cut-over or post-rollout check fails. It is one procedure for the whole fleet in one window; there is no partial rollback of a subset of nodes.
2. Material. Stage keeps `paxd.pre-<RELEASE_ID>` on every host. The snapshot step keeps one archive `<home>-pre-v6.12.0.tar.zst` of the whole data directory, `priv_validator_state.json` included, for every validator and full-node home, taken after the node halted or was stopped at H and before its binary was swapped. `tools/release/rollback.sh --readiness` checks the previous binary on every host and one archive per home before the swaps continue. Neither the binaries nor the archives are deleted before post-rollout verification passes.
3. Procedure. Every node halts. On every validator and full-node home `tools/release/rollback.sh --execute` stops the units, moves `data` to `data.v6.12.0-<RELEASE_ID>`, extracts the home's snapshot, restores `paxd.pre-<RELEASE_ID>` with the atomic swap, removes `data/upgrade-info.json` (sdk/x/upgrade/keeper/keeper.go:453-475), sets `halt-height = 0` (sdk/server/config/toml.go:42) and restarts the units.
4. Signing. The restored `priv_validator_state.json` records H, so the validators sign H1 again on the previous binary; no node runs the set-aside data, so no key signs a second H1 on another chain.
5. Set-aside data. `data.v6.12.0-<RELEASE_ID>` is kept for analysis and is never started; it is removed only by an explicit operator decision.
6. Receipt. `rollback.json` records `readiness`, `rollback_executed` and `result`. The rehearsal runs the same procedure in its rollback leg and records `rollback_rehearsed`.

## Post-rollout verification

1. Script. `python3 tools/release/fleet_check.py --env-file <file> --phase <phase>` checks every node named in the env file and exits 0 only when every check passes. Its phases are `inputs`, `preflight`, `frozen`, `validators`, `oracle`, `services`, `full` and `post`.
2. Checks per node: ABCI info version `v6.12.0` (consensus/internal/rpc/core/routes.go:71); latest height above H1 and not catching up (consensus/internal/rpc/core/routes.go:38); `q upgrade applied v6.12.0` at H1; the block hash at H1 equal on every node (consensus/internal/rpc/core/routes.go:46); every served address of contracts/address-table.md answering its view call without revert (presence by view call, since GetCode reads only the code store, modules/evm/keeper/code.go:15-21); 0x1026 and 0x1027 without code; the launchpad pool count at 0x1017 equal to the rehearsal count; `totalMarkets()` at 0x1015 and `getMarketCount()` at 0x1020 equal to eighteen; `getPrice(m).fresh` for every market; `getFeedKey` returning one key for every bonded validator; the uhpx and SID pointers through `getNativePointer` of 0x100A (precompiles/pointerview/pointerview.go:18, precompiles/pointerview/pointerview.go:24) with decimals 6; USDL `decimals()` 6 at 0x85FcD13735F4309833A503EE804ea32395851479.
3. Services. The `services` phase checks `/healthz/ready` of every data service and `/api/build-id` of the application (Hyperpax:deploy/scripts/deploy.sh:147) against the deployed build id.
4. Receipt key set. With `--receipt <path>` every release script writes a JSON summary of counts and pass flags whose keys come from one set only: `version`, `plan`, `nodes_checked`, `nodes_passed`, `precompiles_served`, `pools`, `markets`, `oracle_fresh`, `feed_keys`, `homes_archived`, `hosts_staged`, `units_active`, `services_ready`, `readiness`, `rollback_executed`, `rollback_rehearsed`, `new_bin_sha256`, `inputs_sha256`, `inputs_approved`, `tag`, `release_sha256`, `result`. No height, host or endpoint enters a receipt. The window receipts are halt-height, preflight, stage, frozen, snapshot, swap-full, validators, oracle, services, full, automation, rollback and post-rollout; with rehearsal and completion they make fifteen.

## Price sidecar

1. Artifact. `price-sidecar-v6.12.0-linux-amd64` is the binary `price-sidecar` of the workspace member `hosted/feeder` (platform/Cargo.toml:23), added by pricefeed task 5.2.6 beside the `layerx-oracle-feeder` binary of platform/hosted/feeder/Cargo.toml:8-10, and built by the release script with `cargo build --locked --release` under the pinned Rust toolchain; its sha256 is a line of `SHA256SUMS`.
2. Install. Each validator host installs the binary with `tools/price-sidecar/price-sidecar.service` and a filled `tools/price-sidecar/config.template.json` (contracts/pricefeed.md, Install); the feed key and the Chainflow key are loaded as systemd credentials, never written into the unit or the config.
3. Feed key. `tools/release/feed_key.py new` writes a secp256k1 secret as 64 lowercase hex digits with mode 0600, the format the sidecar key loader reads (platform/hosted/feeder/src/lib.rs:492-511), and prints the 33-byte compressed public key. `tools/release/feed_key.py payload <pubkey>` prints the calldata of `registerFeedKey(bytes)` of 0x1020.
4. Registration. After H1 each operator associates its operator EVM address with `paxd tx evm associate-address` (modules/evm/client/cli/tx.go:81), sends the payload to 0x0000000000000000000000000000000000001020 with `paxd tx evm call-contract` (modules/evm/client/cli/tx.go:304), then checks `getFeedKey` and `getValidatorByFeedAccount` (contracts/pricefeed.md, Activation item 4), starts the sidecar and waits for `/readyz` 200.
5. Old feeder. The earlier units `layerx-oracle-feeder`, which send `pushOracle` to 0x1015 (platform/hosted/feeder/src/lib.rs:62), are stopped and disabled on every host before H; the stage script reports them.

## Cut-over

1. Data services. After the oracle phase passes, `perps-data-indexer` starts with `PERPS_START_HEIGHT` = H1 (contracts/data-services.md), then `perps-gateway`, `perps-explorer` and `perps-portal`, each only after the previous answers `/healthz/ready` 200. Charts and market data come from Chainflow; the gateway streams the venue's own fills, book and account state.
2. Application. The Hyperpax release build of feature 6 is deployed with `Hyperpax:deploy/scripts/deploy.sh` and `NEXT_PUBLIC_RELEASE_SPOT_OPEN` empty; `/api/build-id` must return the deployed build id (Hyperpax:deploy/scripts/deploy.sh:147).
3. Spot route. `Hyperpax:src/pages/spot.tsx` returns notFound while `NEXT_PUBLIC_RELEASE_SPOT_OPEN` is unset and renders the spot widgets when it is `1`; the navigation entry and the markets mode follow the same variable. The build with the variable set to `1` is deployed only after post-rollout verification passes.
4. Receipt. `services.json` records `services_ready` and `result`.

## Operator inputs

1. Templates. `tools/release/env/rehearsal.env.example` and `tools/release/env/rollout.env.example` declare every variable the release scripts and docs/rollout-runbook.md read, each with an empty value; `tools/release/tests/env_templates.test.sh` refuses an undeclared key or a non-empty value.
2. Filled copies. The operator copies each template to an untracked `.env.rehearsal-v6120` or `.env.rollout-v6120` in access-controlled storage and fills it; the scripts refuse an empty key.
3. Halt height. The halt height H is chosen after implementation (decision.11) and entered with the maintenance window, the public notice text and the build host into the operator input table of the access-controlled copy of the runbook. The table is approved before execution; `halt-height.json` records only `inputs_sha256` of the filled table, `inputs_approved` and `result`. This contract carries no values for these inputs.
