# D20: Operator tooling, registry service and agent functions

Status: decided

## Context
layerxctl (cmd/layerxctl/src/main.rs:186), the program registry service (platform/hosted/registry/Cargo.toml:2) and the agent function routes at 0x0901-0x0908 (human/wallet/gateway/src/precompiles.ts:17-25) remain from two execution domains. The routes name addresses with no registered precompile. The functions at 0x0901-0x0904 (orob, clearing, oracle, pofq) have no execution function in this repository.

## Options considered
| Option | Consequence |
|---|---|
| A: keep and port: layerxctl as an operator eth client, the registry as a read cache over the module, the eight functions as real precompiles | Every function stays available; more surface to maintain |
| B: retire layerxctl and the registry service; delete the routes | Less code; the eight agent functions and the operator tooling end |

## Decision
Option A is decided: layerxctl is ported to an operator eth client, the registry service is rebuilt as a read cache over the programs module, and all eight agent functions become real precompiles at 0x0901-0x0908. The semantics of 0x0901-0x0904 come from the earlier implementation, re-specified in the agent contract and implemented anew (D22).

## Consequences
- layerxctl becomes an operator eth client (cmd/layerxctl/src/main.rs:186).
- The registry service becomes a read cache over the module (platform/hosted/registry/Cargo.toml:2).
- Eight real precompiles stand behind the 0x0901-0x0908 routes (human/wallet/gateway/src/precompiles.ts:17-25).
- None of the three surfaces is retired.

## Affects
- Addresses: 0x0901-0x0908
- Modules: layerxagent precompiles, layerxctl, registry service, layerxprograms
