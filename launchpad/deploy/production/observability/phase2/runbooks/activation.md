# Observability configuration activation

Use the admitted runtime binding and configuration revision. Rendering writes private configuration bundles and a manifest without credentials. Diagnostics retain deployment digest, chain125 contract address pins and service ownership; responder/session credentials stay outside exported diagnostics.

Propose through `control.py` using the assigned operator identity and expected journal sequence. Validation consumes current candidate-bound, coordinator-attested native artifacts for all twelve requirements. It rejects missing scenarios, failed recovery, duplicate database effects, invalid exporter privacy, absent ownership rehearsals and missing measured capacity. Native collector and Prometheus validation must bind the same configuration, source templates and reviewed tool identities.

Activate only the validated revision with the current sequence. The durable journal records actor, revision, evidence digest and the immutable rendered bundle. The platform configuration consumer must adopt that exact bundle and report its digest; publishing a bundle does not itself deploy a service. Preserve the previous bundle and journal for rollback. Rollback uses a new reviewed revision and renewed native validation rather than editing an activated record.

Record a critical alert rehearsal with the named responder and commander, acknowledgment within300seconds, customer updates at most900seconds apart and the executed runbook. An unowned alert rejects validation. Collector failures drop telemetry before blocking durable business commits. Credentials remain private mount references.

For phase3, mount a mode0600 authority document owned by the process UID. Its exact fields are `version` (`3.0`), `binding_sha256`, `expires_at`, and `principals`; each principal has `uid`, `actor`, and a nonempty unique `actions` list drawn from propose/validate/activate/reject. Supply `--phase 3` and `--operator-authority-file` on mutation commands. Scope the authority to the admitted binding and expire it within24hours. Denied identities receive only a fixed denial decision, action and sequence. Preserve a complete native SQLite backup before and after every denied action; compare journal authority, rather than relying on process health.

The signed version3.0 scenario manifest retains every version2.0 field and adds `phase3` with exact fields `namespace`, `recoveries`, `control_adversaries`, `zone_loss`, `interrupted_activation`, and `stale_actor`. Every provider inventory entry contains `role`, `environment`, `namespace`, and `endpoint`, with qualification environment and the same isolated namespace. Artifact kind must match its provider role. Capture origins, PostgreSQL, RPC, broker, socket, collector, Alertmanager, resources, invoices, operator, fault control and Prometheus independently.

Each of the twelve `recoveries` entries references an operator artifact with `fault`, `before`, `after`, `incident_timeline` and `resources`. The fault-control capture contains namespace, environment, operation, target_provider, started_at and ended_at. Capture complete PostgreSQL/broker snapshots as `snapshot_id` and rows of unique `identity` plus exact `value`; recovery must reconstruct identical authoritative state. Resource captures have positive cpu_cores, memory_bytes and disk_bytes. Incident timeline entries contain at, stage and deployment_digest, ordered from injected through restored to reconciled. Metric timelines need explicit millisecond timestamps inside the scenario interval.

Capture all four denied actions in `control_adversaries`: action, unassigned actor, unauthorized reason, before/after state artifacts, bounded denial exports and at. Capture stale_actor with old_epoch, current_epoch, accepted_effects (zero) and before/after authoritative captures. Zone-loss capture fields are namespace, environment, zone, before, after, recovered, old_epoch, new_epoch, stale_acceptances and backlog_after; recovery requires a newer epoch, zero stale acceptances and drained backlog.

Interrupted activation capture fields are before, after, recovered, active_binding_sha256, activation_records, bundle_sha256, journal and bundle_manifest. Keep authoritative application state unchanged, capture an authenticated native SQLite journal with exactly one activation for this revision, and hash the recovered native render manifest against the activation record. A complete closed SQLite backup is required; do not copy a live database without its journal. Rehearse on a separate admitted isolated controller before promoting the phase3 controller. Restore artifacts reference before, after and completed_at. Database-effect artifacts contain identity, committed_rows and outbox_rows; both inventories must have the expected count and no duplicate persisted row.

Phase4 release measurement reuses these native failure/security/recovery captures and requires the same namespace and current candidate identity as its D16 run. Missing restore records, duplicate database effects, absent capacity invoices and unowned critical alerts fail the release measurement; green HTTP process health cannot replace them. The resulting lane report is a measurement input to9.1, not authority to activate a production controller. Preserve the prior activated bundle and its journal while recording actual allocation and SLO observations.
