# Recovery contracts and local proof

This phase supplies versioned offline recovery configuration, disabled resource declarations, content-bound backup inventories, exact reconciliation, and durable PostgreSQL restoration epoch primitives. No production provider is configured, and no function executes the command templates or performs live cutover.

Run fresh checks from the repository root:

```
python3 deploy/production/recovery/check.py
```

The runner requires the authorized local `kindle-bootstrap-local-postgres-1` Docker fixture; it verifies Compose project/service labels before creating a random schema inside the exclusively assigned namespace. It checks the schema ownership token before destruction. No user database, bucket, production credential, or global role is accessed. Each subprocess has a deadline. Tests clean only their exact owned schema.

`recovery.configuration` validates required settings; `resources` validates every disabled operational group and rejects missing or weakened WAL, replica, replay, reconciliation, IAM and cutover gates. Targets default to 60-second WAL age, 300-second replication/RPO and 1800-second RTO. These are targets, not measurements. Retention is 35 daily points, 12 monthly snapshots and 365 archive days; changing it requires a reviewed policy revision.

`manifest` binds physical-base and WAL object inventories, PostgreSQL system identity/version/timeline/LSNs, immutable object version IDs, a single database snapshot, all five authoritative table groups, and chain125/source/interface/deployment/checkpoint digests. The offline `restore_plan` requires a manifest digest from an independently trusted inventory; a self-provided hash is not authentication. It rejects missing coverage, wrong source identity, target times outside archived WAL coverage, or changed encryption references. It always leaves traffic cutover disabled. The provider must verify physical base manifests and WAL continuity/content, target timestamp semantics and actual committed checkpoint after replay. Metadata declarations alone do not prove any of these.

`verify_objects` is a local POSIX object-fixture adapter: bounded chunked checksum reads, regular files only, descriptor-relative no-follow path traversal, and explicit missing/corrupt errors. It does not implement remote object-version lookup, encryption, object locking, replication or IAM enforcement. The production adapter must retrieve the exact pinned version and prove independent-region accessibility. Required authoritative metadata/media replicas block health/cutover when missing; ephemeral CDN and live-playback sessions are rebuilt, never restored as authorities.

`raw_partition` validates bounded, ordered chain125 raw-log identity with committed block-hash and transaction-position consistency. Archive rebuild never substitutes application events for chain events: verified stream backups cover only their exact epoch/hot window, raw-chain archives supply chain history, and PostgreSQL business/outbox/inbox supply application effects. These sources require provider-specific streaming readers and replay integration.

`reconcile` compares exact counts, arbitrary-size unsigned integer amount strings, event-identity digests and the entire fixed checkpoint; missing fields and mismatches block success. `measured_evidence` requires timestamped metric samples, deployment/source/input/inventory hashes, fault interval and explicit outcome/limitations. Accepting the evidence shape does not certify its measurement provenance or evaluate RPO/RTO; the release evaluator must bind fresh trusted runner outputs and enforce targets.

`epoch.sql` is an unregistered SQL resource. Its epoch guard takes a shared row lock through the caller transaction; activation takes an exclusive lock, compares the prior epoch/revision, requires a validated proposal and externally verified fencing-proof digest, advances authority, and writes audit atomically. The guard uses a fixed `pg_catalog` search path and schema-qualified objects under a restricted owner. Revoke table writes from application roles and grant only guard execution. Only the recovery coordinator receives activation/proposal/control privileges. An application-supplied actor string or proof digest is not authorization. Coordinator authentication, proposal validation/rejection audit transitions, provider fencing checks and grant registration remain serial integration work.

Every authoritative write/inbox effect must call the guard in the same transaction. Broker acknowledgements additionally require epoch-scoped broker authority, subjects and credential revocation; a PostgreSQL check followed by an unrestricted external acknowledgement is insufficient. Old-primary traffic/network/publishing authority must be revoked before new-region activation. Exactly one region can write; return/failback requires a new reviewed migration and is never automatic.

Actual local tests prove logical `pg_dump`/restore consistency for marker, exact monetary amount, pending outbox, duplicate inbox and watermark; stale epoch/region rejection; one winner in competing cutovers; guard/cutover lock serialization; and authority rollback when audit insertion fails. They do not prove physical base-backup/WAL PITR, real message publishing/ack rejection, lost broker-disk rebuild, provider IAM/KMS denial, object-store replication, monthly/quarterly drills, 72-hour datasets, region loss, RPO/RTO, deployment or production readiness.

The v3 adversarial path in `phase2/` validates native results for all ten recovery scenarios, including explicit denied operations, exact before/after state reconciliation and measured recovery capacity. It preserves v1/v2 interfaces. Signed scenario receipts bind the source, deployment, interface, inventory, provider executable and actual fault interval; absent or failed receipts block activation. `activate_fenced_v3` additionally binds the authenticated database principal and the exact fresh validation digests. The focused v3 gate and isolated provider configuration are described in `phase2/runbook.md`; new source has no implicit production authorization or certification.

`phase4/release.py` adds a read-only live measurement collector and an evaluator for the existing D16 final shared capture. It records exact native metric responses, actual pinned Kubernetes allocations and PostgreSQL snapshots; requires independently signed real recovery receipts and fixed-checkpoint reconciliation; and emits ten machine-readable requirement outcomes. Its [runbook](phase4/runbook.md) distinguishes bounded component measurements from the final24-hour acceptance at gate9.1. No output from this lane certifies capacity or monthly availability by itself.
